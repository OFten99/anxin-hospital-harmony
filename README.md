# 安心挂号 · HarmonyOS 语音分诊挂号原型

老年人对着手机说"我这心口窝发闷，喘气费劲"，App 听懂后推荐科室，再列出附近能挂上号的医院，直接进挂号页。

**鸿蒙原生原型 + 医院自有 H5 挂号 + 云端 ASR/大模型 + 多医院整合**。

## 四、现在是"演示模式"，怎么切成真的

打开 `service/AppConfig.ets`：

```ts
static readonly ASR_ENDPOINT: string = '';   // 填你的语音识别服务
static readonly LLM_ENDPOINT: string = '';   // 填你的大模型服务
static readonly FORCE_DEMO: boolean = true;  // 改成 false
```

`FORCE_DEMO = true` 时不发任何网络请求，点样例直接出结果。改成 `false` 并填上地址后，走真实录音。

**三个必须注意的点：**

1. **别把 API Key 写进客户端。** hap 包能被解包，Key 会被扒出来。正确做法：自建一个代理服务，客户端只拿短期票据，Key 留在服务端。代码里的 `ASR_TOKEN` 只是联调用的占位。
2. **ASR 接口的数据格式各家不同。** `AsrService.recognizeAudio()` 目前按"base64 JSON POST"写的；如果供应商要 multipart/form-data，按它的文档改那一段就行。
3. **方言是最大的不确定项。** 老年人普通话识别率本身偏低，方言更差。选型时先拿真实老人录音测，别信厂商 demo。识别不准时的正确做法是"我没听清，您再说一遍"，而不是硬猜——代码里已经是这个逻辑。

## 五、接医院真实挂号页

> **已经接上了一个真实后端。** 工程内的 `rawfile/his.html` 直接调用「医院门诊管理系统」（Flask + MySQL）的 `/api/mini/*` 接口，看到的是真实科室/医生/号源，挂的号真的写进数据库。演示时可以切到 Web 后台「挂号管理」核对。
>
> 配置项：`AppConfig.HIS_BASE_URL`。
> 完整说明、后端 CORS 改动与回滚方式、演示动线、幂等限制见 **`docs/真实HIS对接.md`**。
>
> ⚠️ 改完后端 `app.py` 后必须重启 `run_web.bat`，否则旧进程不加载新代码，挂号页会报跨域。

改 `model/HospitalData.ets`。每家医院的科室入口长这样：

```ts
dept('cardiology', '心血管内科', true, '今天 15:30')
```

- 第 1 个参数 `deptId`：**必须**和 `TriageData.ets` 里的科室标识一致，否则匹配不上
- 第 2 个参数：科室在**那家医院挂号系统里**的名字（各家叫法不同，比如中医院把神经内科叫"脑病科"）
- 第 3、4 个参数：能不能约、最近号源

要接真实 H5，给 `dept()` 加第 5 个参数：

```ts
// 填了真实地址：点击医院直接加载医院自己的挂号页
dept('cardiology', '心血管内科', true, '今天 15:30',
     'https://reg.example-hospital.com/book?deptId=0301')

// 不填：加载内置模拟页 rawfile/reg.html
dept('orthopedics', '骨科', true, '今天 14:00')
```

切换逻辑在 `Index.ets` 的 `onSelectHospital()`：`HospitalService.hasRealUrl()` 判断 url 是否为空，非空加载真实页，为空加载模拟页。真实页不会做任何 JS 注入，避免干扰医院自身业务。

### 接真实页面之前，必须在现场验证五件事

这五条任何一条不成立，WebView 方案就会打折扣，**建议先拿一家医院试点跑通再推广**。

1. **是否支持带参直达科室。** 多数医院挂号页只能落到首页，用户还得自己再选一次科室——对老人是灾难。得问信息科要直达地址格式。
2. **WebView 里会不会白屏。** 不少医院 H5 校验 User-Agent 或 Referer，只允许微信内置浏览器打开。
3. **登录与实名能否在 WebView 内完成。** 一般可以，但 Cookie 有效期短，老人下次还得重登。
4. **医保结算、在线支付能不能走通。** 这部分常跳到小程序或要求人脸核验，WebView 里基本走不通。
5. **这家医院到底有没有 H5。** 部分医院只有微信公众号或小程序，没有可直链的 H5。

**验证方法**：用手机**系统浏览器**（不是微信）打开候选 URL，走完一次真实挂号流程。如果提示"请在微信中打开"，那 WebView 方案基本废掉，得换思路。

如果确认是 UA 校验，可以设置自定义 User-Agent 伪装，或改用 Want 拉起系统浏览器；但这两招绕不过 Referer 校验和微信 JS-SDK 鉴权，成功率不高，不要指望它能兜底。

### 合规提醒

内嵌第三方挂号页时，跳转前应有明确提示"即将进入 XX 医院提供的第三方服务"，把责任边界划清。否则一旦挂号出问题，用户会认为是你这个 App 的责任。

## 六、分诊规则怎么调

核心在 `TriageData.ets`，两个表：

**`SYMPTOM_RULES`** — 科室规则。每个科室三类词：
- `bodyParts` 部位词（权重最高，3 分）
- `symptoms` 症状词（2 分）
- `contextWords` 病史/人群线索（1 分）

打分后取最高分科室，再按"与次优科的接近程度"打折算置信度。低于 55 分不放行挂号，改为追问。

**`RED_FLAGS`** — 危急信号，优先级最高，命中直接跳红色警示页，不走普通挂号。当前有 7 条：胸痛+大汗、嘴歪+半身无力、呕血黑便、静坐喘不上气、剧烈头痛+呕吐、晕倒、剧烈腹痛。

> 这套规则是**示例**，不是医学结论。上线前必须让医院医务科或全科医生逐条过一遍，并且改成服务端下发——否则每次调词表都要发版。

**为什么不让大模型直接输出科室？** 三个原因：

1. 科室命名不稳定，同一句话今天说"心内科"明天说"心血管科"，没法对上医院挂号系统的科室 ID；
2. 危急症状必须确定性拦截，不能交给概率；
3. 要向老人解释"为什么推荐这个科"，规则命中的词可以直接展示，大模型的理由不可靠。

所以分工是：**大模型负责把话说清楚（抽结构化症状），规则引擎负责下科室结论（确定、可解释、可审计）。**

## 七、合规红线（这条别踩）

- **不能出现"诊断""确诊""您可能是 XX 病"这类表述。** 一旦涉及疾病判断，就进入医疗器械监管范围，需要拿证。当前定位是"科室推荐 / 挂号导航"。
- 界面必须持续可见"不提供诊断建议，紧急情况请拨 120"。
- 老年用户的语音是敏感个人信息，采集前要有明确告知和授权，音频不要长期留存（当前实现录完即用，未做本地持久化）。

## 九、接微信小程序（导流模式）

产品定位更接近"识货"：本 App 不挂号、不交易，只负责判断挂什么科、去哪家医院，把用户送进医院自己的挂号小程序。

**技术结论（已核实官方文档）：鸿蒙 App 拉起指定微信小程序，官方支持。** 微信 Open SDK for HarmonyOS 从 1.0.3 版本起提供 `LaunchMiniProgramReq` 接口。

三个硬约束：

1. 必须在微信开放平台注册**移动应用（平台选 HarmonyOS）**并过审，拿到自己的移动应用 AppID。企业资质 + 审核，几天周期，这一步没过代码写了也调不通。
2. 需要每家医院的**小程序原始 ID（gh_ 开头）**。
3. 需要目标页面的 **path**——这个只有医院开发方知道。**没有医院配合，只能拉起小程序首页，无法直达科室。**

完整接入方案、代码、失败场景处理见 **`docs/miniprogram-integration.md`**。

### 当前代码状态：拉起链路已接通，只差两个 ID

工程里已经装好 `@tencent/wechat_open_sdk@1.0.23`，`querySchemes` 已加，调用逻辑写在 `service/MiniProgramLauncher.ets`，选医院时优先拉起小程序、失败自动退回 H5。

要启用，只需改 `AppConfig.ets` 里两个常量：

| 常量 | 填什么 | 从哪拿 | 当前状态 |
| --- | --- | --- | --- |
| `WX_MOBILE_APP_ID` | 本应用自己的移动应用 AppID（`wx`） | 微信开放平台 → 移动应用（平台选 HarmonyOS） | ⬜ 待申请 |
| `WX_MINI_PROGRAM_ORIGIN_ID` | 目标小程序的**原始 ID**（`gh_`） | 小程序后台 → 设置 → 基本设置 → 账号信息 | ✅ 已填 `gh_xxxxxxxxxxxxxxxx` |

> ⚠️ 常见错误：把小程序的 AppID（`wx` 开头，用于上传代码）填进 `ORIGIN_ID`。拉起需要的是 `gh_` 开头的原始 ID，两者不通用。

科室到 HIS `department_id` 的映射填在 `model/MiniProgramMap.ets`。没填的科室会退到小程序首页，而不是拼一个查不到医生的空页面。


> 说明：URL Scheme / URL Link 那条路对第三方不可行——生成接口要用小程序自己的 access_token，且 2022 年 4 月后规则改为"一条链接只能被一个用户打开"，无法做批量配置。

如果暂时接不了小程序，退路有三条：

1. 继续用医院 H5（当前方案）
2. 引导用户复制链接到微信打开（体验断裂，不推荐）
3. 做鸿蒙元服务，让医院把自己的挂号能力上架成元服务（体验最好，但要医院配合改造）

## 十、可借鉴的开源资源（已核实）

以下几个方向查过，结论写在这里，避免重复调研。

### 1. 离线语音识别：sherpa-onnx 鸿蒙 HAR 包

- 仓库：`chuanis/harmonyos-next-sherpa-har`
- 性质：Sherpa-ONNX 在纯血鸿蒙上交叉编译好的 HAR，走 NAPI 桥接 C++ 核心，提供 `OnlineRecognizer` / `OfflineRecognizer`
- 许可：MIT（可商用，保留版权声明）
- 集成：编译 `sherpa_onnx` 模块 → 取 `sherpa_onnx.har` → 放 `libs/` → `oh-package.json5` 里 `"sherpa_onnx": "file:./libs/sherpa_onnx.har"` → 把模型放沙盒再初始化

**为什么这一版没用它：** 需要自己下模型、跑 CMake 交叉编译，且该仓库 star 数为 0、只有一次初始提交，工程质量未经社区检验。**但它是这个产品最该走的长期路线**——老年人在家、网络差、语音又是敏感信息，端侧离线识别比上传云端更合适，还顺带解决了 API Key 不能放客户端的问题。等云端方案验证完分诊逻辑，建议切到这条。

### 2. 分诊架构参考：Health-Flow

- 仓库：`Hubert-hwk/Health-Flow`
- 它做的分诊策略：**显式关键词计分优先（血糖→内分泌、血压→心内），关键词无命中才调 LLM 做意图分布**，输出科室 + 置信度 + 风险等级 + 低置信降级标记
- 这个路线和本项目一致，可以从侧面说明"规则优先、模型兜底"不是拍脑袋

**值得直接借鉴的一点：安全护栏。** 它在模型输出之后加了一层确定性规则，一旦出现具体剂量、明确诊断、仅凭单一指标下结论、危急症状缺少就医提示，就把输出替换成保守话术。本项目已按同样思路实现了 `SafetyGuard.ets`——不是靠提示词约束模型，而是在输出后拦截。

**注意：** 我没在它的 README 里看到许可证声明，**用它的代码前必须自行确认 LICENSE**。目前本项目只借鉴思路，没有复制任何代码。

### 3. 扩充分诊词表：中文医疗语料

- 仓库：`fighting41love/funNLP`（84k star，持续更新）
- 里面有：医学词库、中文医疗对话数据集、中文医学 NLP 公开资源整理、医疗实体识别模型与标注语料

**这是当前最该补的短板。** 现在的 `TriageData.ets` 只有约 100 个词，靠人工列举，覆盖不了真实老人的说法。正确做法是：

1. 从中文医疗对话语料里挖出真实主诉表达（尤其是口语、方言变体）
2. 统计高频症状词，按科室归类
3. 用真实语料做回归测试，看误分诊率

顺带说一句，本项目在自测时确实踩到过坑：「心口发闷，喘气有点费劲」最初被判成"置信度不足需追问"，因为词表只收了规范的「胸闷」，没收「发闷」「费劲」；「腿还有点肿」也因为中间隔了字而漏掉了心源性水肿的信号。**这类问题靠拍脑袋列词是发现不了的，必须有真实语料回归。**
